## 限制與驗證邊界

- **測試只在 GitHub Actions 跑**（`tests.yml`，分支用 `gh workflow run tests.yml --ref <branch>`），不在開發機跑；
  本機只做資料作業（抓來源、寫 DB、重生報表）。2026-09-26 由使用者決定。
- **改 workflow 或 scraper 要在 runner 上驗證時，用臨時分支**：`daily-scraper.yml` 以 `workflow_dispatch` 跑在臨時分支上，
  資料只會 commit 到那個分支，不影響 `main` 與網站。跑完刪分支。
  **不要在 `main` 上白天手動觸發**：第一金會提前寫入前一交易日的持股、最新一份報表被整份重生。
- **DB 是 binary，bot 與開發機排程都會 push**：主班次 Cloudflare 觸發 `workflow_dispatch`（台北 18:25／10:25Z），後備 `schedule`
  2026-11 落在 19:54Z ~ 22:57Z，開發機排程 11:10Z 與 14:10Z。資料修正要基於最新 `origin/main` 並避開這幾個時段。
- **單家補抓不可用 `main.py --<來源>` 裸跑**（會以只含該家變動的字典覆蓋整份日報）：改用
  `daily_update_<來源>(generate_report=False)` 只寫 DB，再 `generate_consolidated_reports()`。
- **重生已發布的報表一律用 `scripts/pinned_reports.py`**（其他 ETF 固定在發布時的 `data_date`；見 `date-alignment.md`）。
  改 DB 之前先跑 `--control`，確認重生結果與發布版逐位元組相同。`scripts/regenerate_reports.py` 現在也走同一條路。
- 請求日期來源（只剩國泰）的錯位搶救：先刪錯位群組再重跑（不刪會留孤兒列），重跑必須在事故當日的 UTC 日內；
  細節在 `.ai/archive/handoff-2026-09-26.md`「08-05 錯位資料搶救」。
- 各投信歷史查詢的抓取腳本與收盤價檢驗的腳本沒有進 repo（2026-11-27 用的那批在工作階段的暫存資料夾）；各家怎麼查歷史

  （舊的 `stk_quote_result.php` 不理會日期）。
