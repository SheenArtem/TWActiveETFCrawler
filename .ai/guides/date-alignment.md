# 日期錯位防護指南

**什麼時候讀：** 改 `Database.insert_holdings()`、改 scraper 的日期欄位、或改報表的日期邏輯。

## 防護本體（寫入層）

`Database.insert_holdings()` 在寫入前會逐 (ETF, 日期) 檢查：**若這次抓到的持股與該 ETF
前一交易日逐列完全相同（股票、股數、權重全同），判定為來源尚未更新當日資料，不寫入並記 WARNING。**
開關為 `REJECT_DUPLICATE_OF_PREVIOUS_DAY`（預設開啟）。測試見 `test_duplicate_guard.py`。

## `source_dated` 契約

**防護只對「用請求日期」的來源生效。** scraper 若確實從來源取得資料日期，就在每列帶
`source_dated=True`，防護會跳過該群組。目前 26 檔中已有 **25 檔（14 家投信）**跳過防護：
中信、富邦、第一金、聯博、統一（Excel 表頭與 API 的 `TranDate`）、台新、安聯、群益（buyback API 路徑）、
兆豐、凱基、永豐、摩根（PCF 表頭 `NAV Date`）、野村（API `NavDate`）、復華（Excel 表頭 `日期:`）。
仍受防護的僅剩**國泰（00400A，唯一真正依賴防護的來源）**，
以及所有 scraper 的「解析失敗退回請求日期」備援路徑。

規則只有一條，但很容易寫錯：**`source_dated` 必須只在真的解析到來源日期時才設 True；
任何解析失敗、退回請求日期的路徑都要維持 False。** 群組內旗標不一致時，防護會保守地繼續攔截，
避免漏設一列就整批放行。`source_dated` 只是寫入層的判斷依據，不會寫進 `holdings` 資料表。

## 為什麼要分開

對用請求日期的來源，被擋掉後當天稍後的班次還有機會補上真實資料。
但對已用來源日期的 scraper，來源日期會往前走（隔天只給隔天的檔案），
**被擋掉的那天再也抓不回來，是永久缺資料**。而且對它們來說「內容與前一日相同」
是可以判讀的：來源日期已經前進了，內容沒變就是真的沒調整，擋下來純屬誤擋。

## 摩根的判法：直接讀 PCF 表頭 `NAV Date`（`Valuation Date` 退為備援）

摩根 PCF 表頭列（`Record Type='H'`）同時帶有兩個日期欄位：

- **`NAV Date`（`YYYYMMDD`）＝持股／淨值基準日（2026-10-27 起採用）**：直接解析為資料日期並標
  `source_dated=True`。當日 PCF 尚未更新、或遇上未及列入 `trading_calendar.py` 的臨時颱風假時，
  寫入日期仍停留在真實持股日（UPSERT 不刷新既有 `created_at`），不會在 DB 產生假日期或假報表。
- **`Valuation Date`（`YYYYMMDD`）＝下一交易日的申購買回適用日（僅作 `NAV Date` 缺漏時的備援）**：
  2026-08-05 第二批原以「`VD ＞ 請求日` 夾回請求日」判讀新檔，但這個判準假設請求日本身必為交易日——
  2026-09-25（中秋，當時尚未加交易日曆）與 2026-10-23（臨時颱風假）都曾把前一交易日的檔案夾成假日寫進 DB。
  改以 `NAV Date` 為主後已從根源消除此問題。

## 請求日期與報表日期都要落在交易日

main.py 各來源的請求日期、合併報表的日期上限，一律走 `src/trading_calendar.py` 的
`last_trading_day()`：週末與證交所休市日都退回最近一個交易日。即使摩根已改讀 `NAV Date` 不再產生假報表，
交易日曆對「以請求日當 PCF 適用日查詢」的來源仍然必要：2026-10-23（五）颱風休市未即時補入日曆時，
第一金查詢 `pStrDate='2026-10-23'` 就提前一天拿到 `sdate='2026-10-22'` 的持股（把原本應留在下一個開盤日才揭露的變動提前寫入）。

- 休市日取自證交所「市場開休市日期」，**每年要補下一年**：`.github/workflows/trading-calendar.yml`
  每週一檢查，公布後由 `scripts/update_trading_calendar.py` 補上、跑完測試開 PR，合併才生效。
  未涵蓋的年份只排除週末並記一次 WARNING。清單裡的「開始交易日／最後交易日」有開盤，不能收；
  颱風休市不在清單內，要手動補。
- 假日班次是**退回**而不是整班跳過：照樣去抓，晚發布的來源還能補上最後一個交易日的資料。
- 多數來源的日期參數是 PCF 適用日（第一金、兆豐、統一 API），假日查詢回 0 筆；
  要補某個交易日的持股，得查它的下一個交易日（見 `data-sources.md`）。
- **不要替固定落後一天的來源（第一金、00988A）預先補最新交易日。** 一份報表每檔只帶一個資料日期，
  最新一份又會被每個班次用當下的 DB 整份重生：補進去之後它跳到新的資料日期，前一份報表是再前一天，
  中間那天的變動就不在任何報表裡。2026-09-26 補第一金 09-24 就漏掉了 09-23 的變動，已撤回；
  讓下一個交易日的班次照常抓回即可。

## 為什麼還需要它

國泰的 API 無法從回應判斷真實日期（對未發布的日期會**靜默回退**到前一日、
回應中沒有任何日期欄位可識破），是唯一真正依賴防護的來源。此外它也守著
所有 scraper 的備援路徑（解析失敗退回請求日期時 `source_dated=False`）。
2026-02~08 期間共 15 個交易日出現錯位（61 組），集中在安聯（21）、群益（17）、
台新（7）——這三家已於第二批轉換，歷史群組已刪除、報表已重生。

**仍存在的誤判風險：** 受防護的來源（國泰）若某天真的一股都沒調整，會被誤擋、
當日缺該檔資料。機率低，且缺資料比留假資料好；真的需要放行時用環境變數關閉。

## 下游影響：報表要逐檔回退日期

各家投信的資料日期天然不同步——當日 PCF 的發布時間各家不同，晚發布的要到收盤後才更新——
防護生效當天當日有資料的 ETF 又會更少。所以報表**不能用單一日期去撈**：

- 持股總覽逐檔取各自最新可得的日期（`Database.get_latest_date_on_or_before()`），
  不會讓落後一天的 ETF 從總覽消失；每檔的實際資料日期以 `data_date` 標在卡片標題上。
- 報表日期本身取 DB 內實際最新交易日，並夾住不晚於最近一個交易日（摩根估值日領先一日，
  不夾會顯示未來日；DB 若混進假日的列，也會被夾回前一交易日）。

## CI 早退守衛與 `created_at` 的契約

`.github/workflows/daily-scraper.yml` 的早退守衛看「今天**首次寫入**過幾檔 ETF」
（`holdings.created_at`，UTC），達覆蓋率門檻才跳過整個爬蟲。

判準不能用「資料日期是否等於今天」——各家資料日期天然不同步，那樣會把正常落後一天的檔算成沒跑。
也不能只看「有沒有寫過」——主班次只要一檔成功就成立，其餘失敗的檔就再也沒有後備班次去補。

**門檻自 2026-11-27 起是 100%**（全部寫入才跳過；repo 變數 `SKIP_COVERAGE_PCT` 可調）。原本的 70%
在追蹤到 23 檔之後形同永遠跳過：即使 3～5 檔的來源當天失敗，寫入仍有 18～20 檔（78～87%），
2026-10-27 ~ 11-26 的 22 個交易日有 21 班後備被跳過，當天失敗的來源（安聯 11-09 頁面沒渲染、
摩根 11-16 的 PCF 晚發布）沒有第二次機會。兆豐在 runner 上抓不到，由開發機的排程在主班次之後補進來
（見 `data-sources.md`）；它補的列一樣有當天的 `created_at`，所以開發機有補到、其他 25 檔主班次也都寫入時
後備班次會被跳過，開發機沒補到的日子後備班次照跑。

同一支 workflow 裡還有兩個相鄰的機制：

- **延遲跨日的後備班次整班跳過。** `schedule` 的 cron 是 13:00Z，GitHub 的延遲在 2026-11 已拖到
  7～10 小時，11-23 那班延遲到隔日 00:40Z 才起跑。跨過 00:00Z 之後 `main.py` 的請求日期變成還沒
  收盤的下一天：第一金查那天會提前拿到前一交易日的持股，最新一份報表跟著被整份重生、它的資料日期
  往前跳（那一班把 11-23 報表裡第一金的資料日期從 11-20 改成 11-23；對照首次發布的版本，第一金
  11-19 → 11-20 剛好沒有變動，所以那次沒有漏掉東西）；國泰對還沒發布的日期會靜默回前一日的內容，
  前一天若沒寫入就會被當成今天寫進去。守衛步驟一開頭就把「`schedule` 觸發、卻在 10:00Z 以前起跑」
  的班次跳過。
- **來源停更警報**（`scripts/check_stale_sources.py`，在 commit／push 之後跑）：有 ETF 的最新資料
  落後最近交易日達 3 個交易日（`STALE_TRADING_DAYS`）就讓班次失敗、GitHub 寄信。沒有它的時候，
  來源改版或被擋只在 log 留一行 ERROR、班次照樣是綠的；2026-11 中信、聯博、兆豐各停更 2～5 週
  都是人工稽核才發現。repo 變數 `STALE_IGNORE` 可以列出已知抓不到的 ETF（只印 warning、不讓班次變紅），
  預設不忽略任何一檔。**這一步同時是兆豐本機排程的警報**：兆豐靠開發機每天補，平常在這裡是落後
  1 個交易日；開發機連續 3 個交易日沒補到，班次就變紅。

**`created_at` 的語意是「該列首次寫入時間」**：`insert_holdings()` 是 UPSERT，
衝突時只更新數值欄位、不動 `created_at`。這是守衛正確性的必要條件——
source_dated 豁免達 22/23（96%，已過 70% 門檻；2026-08-05 轉換後是 14/19，
2026-08-09 新增兆豐／凱基／永豐三檔後 17/22，2026-09-03 新增 00988A 後 18/23，
2026-10-27 補齊野村三檔與復華一檔後為 22/23）後，若「來源沒更新、重寫同一個
資料日期」會刷新時間戳，「全來源停更」的傍晚會誤達標跳過後備班次，晚發布的來源
（如聯博常 18-19 點才更新當日檔）那天就永久缺資料。改 `insert_holdings()` 時
**不得**讓任何路徑覆寫既有列的 `created_at`；`test_duplicate_guard.py` 的
UPSERT 區塊守著這件事。

## 報表的三個產出點必須一致

持股總覽只能從 `ReportManager.build_etf_holdings()` 出來，它負責逐檔回退並帶上
`data_date`。報表 payload 只有一個出口，全部都要走同一套日期規則：

| 產出點 | 持股總覽 | 變動追蹤 |
| --- | --- | --- |
| `ReportManager.generate_all_reports()`（每日班次） | `build_etf_holdings()` | `detect_changes_batch()`，再拿掉沒有新資料的 ETF（`find_stale_etfs()`） |
| `scripts/pinned_reports.py`（重生已發布的報表、本機回補兆豐） | 開暫存 DB 後呼叫 `generate_all_reports()` | 同上 |
| `scripts/regenerate_reports.py`（名稱或資料修正後重生） | 轉交 `pinned_reports.regenerate()` | 同上 |
| `scripts/render_report_pages.py`（更新首頁與日報的共用版面） | 已發布的逐日 JSON | 從 `src/templates/site.html` 重繪頁面，沿用報表當時的數據與產生時間 |
| `HTMLReportGenerator.generate_dashboard_data()` | 沿用傳入的 `etf_holdings` | 由 `etf_holdings` 取 `data_date` 標到 `detailed_changes` |

新版日報的 `report_schema_version` 為 2。每檔的 `previous_data_date` 是分析器實際使用的上一個持股日，
`previous_report_data_date` 是上一份可讀報表列出的持股日。`comparison_kind` 區分相鄰交易日
（`daily`）、跨期（`interval`）、首份快照（`first`）及交易日無法確認（`unknown`）。
報表頂層另列 `previous_trading_date` 和 `previous_report_date`。新持股即使數量全數相同，也可產生當期報表。
已發布的舊 JSON 沿用原格式重生，使 `pinned_reports.py --control` 能繼續核對原始位元組。

回填腳本曾經自己組一份持股總覽（單一日期、沒有 `data_date`），結果是回填出來的
`docs/data_*.json` 全部掉了 `data_date`、首頁「資料日期」欄整排顯示 `—`，
而且同一份報表的兩半各用一套日期規則。**不要再各寫一份。**

## 重生已發布的報表：`scripts/pinned_reports.py`

新版網頁從新日報直接讀取每檔基金的前次持股日。舊格式報表的日期對照存放在 `docs/assets/report-baselines.json`，以報表日期、產生時間和基金來源日核對。回補或重生舊格式日報後，執行 `python scripts/build_report_baselines.py` 重建日期對照，再用 `python scripts/render_report_pages.py` 同步靜態頁。只改 HTML 模板時可直接執行後者。

事後補進或修正了某幾檔 ETF 的持股（本機回補兆豐、來源停更後回補、歷史日期改標），要讓那幾天的報表
反映出來時用它。**不能整份重生**（每檔取不晚於報表日期的最新資料）：固定落後一天的來源（第一金、00988A）
事後 DB 已經補齊，整份重生會把它們在舊報表裡的資料日期整串往前推，原本那一天的變動就不在任何報表裡了。

- 做法：每個報表日期開一個暫存 DB，指定的 ETF（`--etf`）放不晚於報表日期的列，其他 ETF 只放不晚於
  發布時 `data_date` 的列，再走 `generate_all_reports()`。寫回前逐檔核對：沒指定的 ETF，持股與變動
  必須與發布版相同，否則那一份與它之後的都不寫回。
- `--refresh`：資料日期不動、但那一天的內容在 DB 裡修過（刪掉不該存在的列、改了名稱對照表）。
  固定落後一天的來源要修內容時用這個，不要用 `--etf`。
- `--control <日期…|all>`：全部固定、不指定任何 ETF，重生結果必須與發布版逐位元組相同。改 DB 之前先跑，
  確認這台機器與現行程式重現得出線上的報表。2026-11-27 整批重生之後，`--control all` 是全部通過的。
- `--create <日期>`：補一份當天沒有產生的報表（每檔取不晚於那一天的最新資料）。
- 內容有變的報表，更新時間改成重生的時間；內容沒變的不寫回。最新一份報表不用另外固定：之後每個班次
  （含週末、假日）都會用當下的 DB 整份重生它。
- 2026-11-27 用它把整個報表庫重生過一次：08-04 以前的報表讓日期修正過的 8 檔取新資料、清掉第一金的
  彙總列、補上缺的 05-26、刪掉 02-12 與 02-27 兩份非交易日報表，並把「沒有新資料就不重列變動」套到每一份。

## 防護擋不到的錯位：整串平移

防護只認得「今天的內容和前一天一模一樣」。若來源**每天都**把前一交易日的持股標成今天，
每天內容都不同、只是整串往後移一天，防護永遠不會觸發，網站上每一天都錯一天。

實例：00981A 自 2026-07-31 起 Excel 解析失敗、每天退回統一 API，而 API 的日期參數是
PCF 適用日、回來的是前一交易日的持股（`TranDate`）。整串晚一個交易日持續到 09-24，
直到連假讓 09-24 的持股歸在 09-29 底下才被使用者發現；只有第一天（07-31，內容等於 07-30）
被 08-05 的歷史清理當成錯位刪掉。修法與回補見 `data-sources.md` 的統一列。

要抓這種錯位，只能拿**另一個明確標示持股日期的來源**逐筆比對同一天的內容
（例如同一家的 Excel「資料日期」對 API），或用收盤價檢驗：持股權重 ∝ 股數 × 持股日收盤價，
拿各候選日期的收盤價去配，配得最好的那天才是真正的持股日。**「API 嚴格遵守請求日期」
不代表請求日期就是持股日**——要先確認那個日期參數是持股日還是適用日。

回補時，整串平移可以由舊到新逐日改標（`date=P` 改成 `TranDate(P)`，目標日期都是上一步
剛騰出來的），但要先驗證每天的內容和 API 逐筆相同、`TranDate` 一路剛好接回前一個日期。
重新產生歷史報表時，**其他 ETF 要固定在發布當時的 `data_date`**，用 `scripts/pinned_reports.py`
（見上方「重生已發布的報表」）。

## 沒有新資料的 ETF：變動只列一次

變動是逐檔比對「各自最新可得的資料日期」得出的，來源某天沒前進時 `detect_changes_batch()` 會回同一批
變動。2026-11-27 以前每日報表會把它再列一次：中信、聯博、兆豐停更期間，每日報表有 25～57% 的變動是
2～5 週前的舊資料，看起來卻像當天的。

現在的規則（`ReportManager.find_stale_etfs()`）：**這一份報表的資料日期與上一份已發布報表相同＝自上一份
以來沒有新資料**。這些 ETF 的持股照樣留在持股總覽（最後一次抓到的內容），但變動不重列，改列在
`stale_etfs`（ETF、資料日期、落後幾個交易日）：

- JSON 有停更檔才輸出 `stale_etfs`。摘要、索引與熱門股票都只算有新資料的 ETF。
- 靜態日報列出未更新檔數，逐基金明細標出實際比較日期，Markdown 與純文字報告各有一段。
- 互動首頁從所選日的涵蓋摘要及來源清單查閱逐檔狀態。

## 已知取捨與殘留風險

- **上一份報表是判斷基準。** 「沒有新資料」是拿上一份已發布報表的資料日期來比，所以重生某一份報表時
  要由舊到新處理、後一份拿前一份重生後的資料日期（`pinned_reports.py` 會做）。資料晚到、隔天才跟著
  下一天的資料一起進 DB 時，晚到那一天的變動不在任何報表裡（報表只比對相鄰兩個資料日期）；
  要補就用 `pinned_reports.py --etf` 重生晚到那一天的報表。
- **前一交易日沒有資料時，防護必然放行。** 防護是拿內容跟「該 ETF 前一個有資料的日期」
  比對，沒有基準就無從比起（`_duplicates_previous_day` 回傳 `(False, None)`）。
  新上市、長假後首日、或該檔連續失敗數日之後的第一次成功，都落在這個窗口內，
  錯位資料會寫進去，而且會讓 CI 守衛的 WROTE 計數加一。這是指紋式設計的固有限制。
  （2026-08-05 的 00406A 首抓正是此例：中午盤中首抓寫入了前一日內容、無基準可擋，
  當晚以刪除＋重抓修復。）
- **群益走 API 的改版風險。** 主路徑改 buyback API 後，欄位改名不會有「下載按鈕壞掉」
  那種明顯訊號；解析器對缺欄位保守退回、並保留 Playwright+Excel 備援（備援不帶
  `source_dated`，防護對它生效）。
